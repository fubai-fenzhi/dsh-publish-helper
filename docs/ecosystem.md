# DSH 生态定位：插件配技能，一套交付

> 一句话：**插件给动作，技能给流程；装一套，用一套；跨套可组合；常驻成本趋近于零。**

## 1. 三层模型

```text
DSH（宿主）
 ├─ 插件（Plugin）      → 能力层：工具、钩子、UI、HTTP 路由
 ├─ 技能（Skill）       → 流程层：步骤、判断、坑（按需加载）
 └─ 组合（Bundle）      → 交付层：插件 + 技能 + 模板，一起装、一起发版
```

| 层 | 谁消费 | 成本 |
|---|---|---|
| 插件 | 模型（工具 schema 每轮可见） | 常驻（约 300–900 token/套） |
| 技能 | 模型（命中才加载） | 0 常驻；命中约 500–800 token |
| 组合 | 用户（一条安装命令） | 安装一次 |

## 2. 定位原则

1. **一套交付**：每个 bundle 同时提供「能做」和「会做」——工具 + 技能，缺一不可。
2. **技能优先**：能写成技能解决的流程，不进工具描述；工具只暴露动作和参数。
3. **硬约束进代码**：安全默认、权限校验、重试策略写在插件里；技能只做建议。
4. **工具数克制**：一套 ≤5 个工具；低频动作拆套或改技能 + CLI。
5. **跨套组合**：技能可以调用其他插件的工具；工具名全局唯一、语义稳定。

## 3. 互操作约定

### 工具命名

- 前缀 = 插件域：`publish_*`、`bili_*`、`procedures_*`
- 动作 = 动词：`_preflight`、`_submit`、`_edit`、`_check`
- 全局唯一，发布后不改名（技能靠名字引用）

### 技能引用工具

技能正文里显式列出用到的工具：

```markdown
## Tools used
- bili_check — login and binary status
- bili_upload — upload with metadata
- bili_edit — change title/partition/visibility
```

规则：

- 只写工具名和作用，**不复制**工具参数说明（避免两处维护）
- 工具缺失时降级：给出可执行的 shell 命令，不假装调用成功
- 跨套引用时标注插件名：`publish_workflow`（来自 dsh-publish-helper）

### 技能命名

- kebab-case，`<域>-<任务>`：`bilibili-upload`、`publish-release`
- 一个技能只做一件事；长流程拆多个技能
- 描述里写「什么时候用」，不要写实现细节

## 4. 组合示例

| 组合 | 插件 | 技能 | 组合场景 |
|---|---|---|---|
| 发布 | `dsh-publish-helper` | `publish-release` | 发版 → 收录 → 撤回 |
| 视频 | `dsh-bilibili-upload` | `bilibili-upload` | 上传 → 核对 → 改可见性 |
| 经验 | `dsh-procedures` | （钩子自动触发 + 卡库） | 报错命中 → 读卡 → 修 |
| 跨套 | publish-helper + bili-upload | `publish-release` 里引用 `bili_*` | 发布插件后录演示视频 |

## 5. Token 账

| 方案 | 常驻/轮 | 说明 |
|---|---|---|
| 纯插件（含全部流程） | 900–1500 | 流程塞进提示，每轮付费 |
| 纯技能 | 0 | 但无法执行动作 |
| **插件 + 技能（本定位）** | **300–900** | 工具最小化；流程按需加载 |
| 省下的部分 | 约 40–70% | 相对把流程写进常驻提示 |

关键动作：

- 工具 schema 只留必要参数（默认值写进参数描述）
- 一个插件不要注册 10 个低频工具
- 技能只在命中时加载；触发条件写准，避免误加载

## 6. 交付清单（每套必检）

- [ ] `dsh.bundle.patch` 可安装
- [ ] 工具名带前缀、≤5 个
- [ ] 至少一个运行时技能（`ctx.skills.register`）
- [ ] 技能声明 Tools used
- [ ] 安全默认在代码里（默认私密、校验、dry-run）
- [ ] README：安装命令 + 一句话 + 技能说明
- [ ] 测试覆盖参数构造与安全校验
- [ ] preflight PASS + npm 发布 + 市场投递
